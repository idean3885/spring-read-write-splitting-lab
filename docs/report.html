각 타일은 single → split. 같은 부하를 두 구성에 차례로 발생시켰습니다.

1. 목적

Spring · JPA 애플리케이션에서 읽기 분리를 어떻게 구성하는지, 구성하면 무엇이 달라지는지 확인합니다.
같은 부하를 읽기 분리가 없는 구성(single)과 있는 구성(split)에 발생시키고, 각 DB 가 실제로 받은 쿼리 수와 지연을 비교합니다.

2. 조건

알아야 할 용어

소스쓰기를 받는 원본 DB. 이 실험의 MySQL 1번 서버(server_id 1)
레플리카소스의 변경을 복제받는 사본 DB. 읽기만 허용합니다(read_only).
MySQL 2번 서버(server_id 2)
읽기 분리조회는 레플리카, 쓰기는 소스로 보내 소스의 부하를 나누는 구성
readOnly 트랜잭션Spring 의 @Transactional(readOnly = true). 이 표시를 보고 레플리카로 보냅니다.
라우팅 데이터소스Spring 의 AbstractRoutingDataSource. 커넥션을 달라는 요청을 받는 순간, 현재 트랜잭션이 readOnly 인지 보고 소스 · 레플리카 중 하나에서 커넥션을 꺼냅니다.
지연 커넥션 프록시Spring 의 LazyConnectionDataSourceProxy. 커넥션 요청을 받으면 대리 객체를 먼저 돌려주고, 첫 쿼리를 실행할 때 진짜 커넥션을 꺼냅니다.

3. 절차

부하동시 작업자 32개가 구성당 30초 동안 쉬지 않고 연산을 보냅니다.
single 을 먼저, split 을 다음에 실행합니다.
구성마다 측정 전 5초 준비 부하를 발생시키고 그 결과는 버립니다(JVM · 커넥션 풀 준비).
연산집계 조회 80%: readOnly 트랜잭션으로 최근 20,000건 사용량의 건수 · 합계를 조회합니다.
원천 적재 20%: 쓰기 트랜잭션으로 사용량 1행을 넣습니다.
판정 지표도착 서버: 각 MySQL 의 문장 이력(performance_schema.events_statements_history_long)을 실행 직전에 비우고 실행 뒤 센 값입니다.
복제는 ROW 형식이라 레플리카가 복제로 적용한 변경은 문장으로 잡히지 않습니다.
그래서 레플리카에 잡힌 SELECT 는 앱이 보낸 것입니다.
교차 확인조회 트랜잭션 안에서 받은 @@server_id (앱이 본 서버 번호)
부가 지표처리량 · 지연 p50 · p95 · p99 · max · 오류 · 복제 지연(0.5초마다 확인)

5. 결론

읽기 분리를 켜면 조회는 레플리카가 받고, 소스는 쓰기만 받습니다.

  • 근거: 집계 조회의 레플리카 도착 비율 single 0% · split 100% (서버 쪽 문장 수), 앱이 본 서버 번호 split 레플리카 7,615건 · 서버 쪽 7,594건
  • 적재 지연 p50 · p99: 20.37 · 69.32 → 8.24 · 17.22 ms
  • 처리량: 312.10 → 314.70 ops/s
  • CPU 평균 (소스 · 레플리카): 100.5% · 4.1% → 3.7% · 95.0%
  • 구성의 요점: JPA 에는 라우팅 데이터소스를 지연 커넥션 프록시로 감싸서 전달(빠지면 조회가 소스로 향함, 명세로 확인)
  • 대가: 복제 지연, 방금 쓴 값을 바로 읽는 조회는 readOnly 없이 소스에서 조회(명세로 확인)
